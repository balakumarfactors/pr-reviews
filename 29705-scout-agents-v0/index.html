Why it exists

Scout can chat and can run saved prompts on a schedule (routines). Nothing owns a long-running goal.

Before

A routine

A saved prompt that runs on a schedule and sends a report. It cannot ask you a question, and there is no single place to follow up on what it found.

Now

A Scout Agent

It owns a goal. It keeps its own notes, runs tasks (routines) on a schedule, asks the owner when it is unsure, and talks to the owner in one private chat. After a run that found something, it can follow up on its own.

What you can use it for

Four things V0 is built for. The example agents are made up.

Watch

Speak up only when it matters

A daily check. When nothing is wrong, the run leaves a quiet "checked, nothing new" note and nobody is bothered. When it finds something, the agent wakes up and tells the owner.

Example: a "Pipeline watcher" agent.

Report

A weekly report that learns

Every Monday at 09:00 a task writes its report to a run thread. The agent keeps notes such as "prefers short reports" and uses them next time.

Example: a "Weekly summary" task.

Ask

Ask when unsure

A run can end with a question. The agent shows as waiting. The owner answers in that run thread and the question clears.

Example: "Should renewals count as stalled?"

Follow up

Act on a finding by itself

After a finding the agent takes its own turn in the owner chat. It reads the full run, and can update its notes, pause a noisy task, or start another run (2 per hour at most).

Example: start a deeper follow-up run on what it flagged.

Owner chat

Private to the owner. This is where the owner talks to the agent. Every finished run leaves a one-line note here, and the agent's own follow-ups land here.

Run thread

One per task run. It holds the task prompt and the report. The whole team can read it. Only the owner can reply, which is also how the owner answers a question.

If the report has a question

Run asksThe run ends with a question for the owner.
Agent waitsIt shows as waiting, with the question.
Owner answersA normal message in that run thread.
Question clearsOnce the reply is stored. If the turn fails, it stays open.

The owner can also stop a run. It notices the stop request at its next model call and ends as cancelled.

Does the agent wake up?

Not every run wakes the agent. All of these must be true. A question asked by the run itself does not block its own wake.

  1. The run succeeded and asked to notify
  2. The agent has used fewer than 6 wakes this hour
  3. The owner is not chatting with the agent right now
  4. The owner chat is not waiting on the owner's answer to an earlier question or approval
  5. LLM quota is left and the services answer
The agent wakes upThe turn runs in the Python service, in the background. The Go side does not wait for it. It is capped like any chat turn (29 minutes by default), and the owner chat is locked while it runs.
If any gate says no: only the one-line note is posted. Nothing is retried and no error is shown.

For the review

The details you need while reading the diff.

Connectors

Each agent has its own connectors (MCP). The owner chooses them.

  • A new agent has none switched on. The owner switches each one on.
  • At most 10 per agent. A connector that can write also needs a separate "allow write" OK.
  • Task runs now get the connectors that are switched on. Before, they got none.
  • This PR adds no way to add a custom connector URL.

Flags and rollout

  • Two new flags, both off by default. One on the API server: when it is off, every agent route answers 404. One on the Python service: it only gates two read tools in plain Scout chat.
  • A flag is a rollout gate, not a kill switch. Turning the API flag off stops the agent routes and agent chat. Agents that already exist keep running their tasks. The wake has no flag, so only a deploy stops it.
  • With all flags off, plain Scout works as before. Tests cover this. A few plain-path changes are on purpose: the run code is split in two (plain routines keep the old entry), inserts name the new empty columns, the sidebar and unread lists hide agent chats, the payload filter skips two agent routes, and removing a member runs one extra statement.
  • Auth. When the agent calls back into the API, it uses the owner's short-lived token. This PR makes that token work on nine more routes: three agent routes (run a task, list runs, edit the agent) and six task routes (create, read, edit, publish, pause, resume). They still check the flag, and the agent routes check that the caller is the owner.

Deploy order

  1. Both database migrations first. Apply the connectors one before the data server rolls out, or every agent turn fails. Staging has only the earlier first migration, so the second must be applied there by hand.
  2. Then the services: data server, Python service, API server, scheduled job. A wake only starts after the API server or the job is new, so Python is always ready first.
  3. Flags last, and only after the image that defines each flag is live. Otherwise the workload crashes on an unknown flag.

What was tested

Quoted from the PR description. I have not re-run these.

Done

  • Go: 354 tests passed across 41 test files. Python: 886 tests passed (631 + 255).
  • One live local run with a real model: the wake replied, it was skipped when the chat was busy or waiting on the owner, and both hourly caps held.
  • When the Python service was killed mid-turn, the chat lock freed by itself in under 90 s. The turn itself was lost.

Not run yet

  • Staging, a real frontend, and a real connector.
  • A wake turn longer than 30 s, so the lock refresh was not seen live.
  • A wake that asks the owner a question, and a wake started by the scheduled job (tests only).
  • An older Python answering 404, Slack and email delivery, and the full test suites.

The one manual check that closes most of this: on a staging agent, Run now a task that finds something, then read the owner chat. Expect the run note, then the agent's reply.

Good places to look hard

  • Permissions. Owner vs member on every route, including the nine token routes.
  • The wake. It uses the same tools as the owner's chat, with nothing locked. Read the "Known limits of the wake" section in the PR description before you approve.
  • Loops and two writers. The wake cap, the wake-started run cap, the turn lock and the notes version check.
